## 1. 引言

### 1.1 文档目的

本文档描述 KK Mod Manager（以下简称"本工具"）的软件需求，作为开发、测试和验收的依据。

### 1.2 适用范围

本工具是一款面向 **Illusion 系列游戏**（Koikatsu / KK 系列）的桌面端 Mod 管理工具，运行于 Windows 10/11（64 位）平台。

### 1.3 术语定义

| 术语 | 定义 |
|------|------|
| **Mod** | 由玩家社区创作的游戏扩展内容包，以 `.zipmod` 格式分发。`.zipmod` 文件本身就是 Mod，由 Sideloader 直接加载，**无需解压** |
| **zipmod** | Sideloader 标准 Mod 格式，本质为 ZIP 压缩包，内含 `manifest.xml` 元数据文件和游戏资源文件 |
| **manifest.xml** | zipmod 内的元数据描述文件，包含 Mod 的 guid、名称、版本、作者等信息 |
| **GUID** | Mod 全局唯一标识符，由 Mod 作者定义，同一 Mod 的所有版本共享同一 GUID |
| **游戏 Mod 路径** | 游戏加载 Mod 的目录（Sideloader 的 Mods 目录），`.zipmod` 文件放置于此路径下的作者分类子目录中 |
| **本地 Mod 仓库路径** | 用户本地存储 Mod 收藏的目录，按作者分类组织，作为 Mod 的集中管理仓库 |
| **远程仓库** | 可选的在线 Mod 存储地址，用户可配置 HTTP/HTTPS URL 指向远程 Mod 仓库 |
| **角色卡** | Koikatsu 的角色数据文件（PNG 格式），内嵌角色外观数据和所依赖的 Mod 列表 |
| **服装卡** | Koikatsu 的服装搭配数据文件（PNG 格式），内嵌服装数据和所依赖的 Mod 列表 |
| **场景卡** | Koikatsu Studio 的场景数据文件（PNG 格式），内嵌场景对象树（角色 / 物品 / 灯光等）与场景设置；每个内嵌角色携带一份完整角色卡数据，物品 / 地图等 Mod 依赖记录在场景级扩展数据块中 |

### 1.4 参考文档

- KKManager 开源项目（同类工具参考）：https://github.com/IllusionMods/KKManager
- KK Library（同类场景 / 卡片库管理工具参考，含场景缺失 Mod 检查与角色提取）：https://kklibrary.dev
- IllusionStudioGet（开源场景角色提取工具参考）：https://github.com/soeminnminn/IllusionStudioGet
- BepisPlugins / Sideloader UniversalAutoResolver（场景扩展数据结构参考）：https://github.com/IllusionMods/BepisPlugins
- Sideloader zipmod 规范

## 2. 产品概述

### 2.1 问题描述

Illusion 系列游戏拥有庞大的 Mod 社区，`.zipmod` 是标准的 Mod 分发格式。用户经常面临以下问题：

- 下载的 Mod 散落在各处，不知道已经收集了多少、缺了哪些
- 复制 Mod 到游戏目录时容易重复或覆盖，版本管理混乱
- 拿到一张角色卡或服装卡时，不知道需要哪些 Mod，也不知道这些 Mod 自己有没有
- Mod 数量一多，无法按作者来快速定位和整理

### 2.2 产品目标

提供一套 Mod 全生命周期管理能力：

1. **双路径管理**：游戏 Mod 路径 + 本地仓库路径，区分"已安装"和"已收藏"
2. **按作者组织**：`.zipmod` 文件按作者名自动归类存放，作者匹配不区分大小写
3. **卡片解析**：拖入角色卡/服装卡/场景卡，自动识别所需 Mod，对比游戏已装和仓库收藏，给出缺失清单
4. **远程仓库（可选）**：支持配置远程仓库地址，为后续联网查询做预留
5. 安全安装 Mod，自动防止重复和版本冲突
6. 可逆地管理 Mod（禁用而非删除）
7. 精确卸载 Mod，不留残留文件

### 2.3 产品范围

**在范围内：**
- `.zipmod` 格式 Mod 的安装、卸载、启用、禁用
- manifest.xml 元数据解析与 GUID 重复检测
- **按作者分类**的目录组织（作者名来自 manifest.xml，匹配忽略大小写）
- **角色卡 / 服装卡 / 场景卡解析**，展示卡片所需的 Mod 及缺失情况
- **双路径**（游戏 Mod 路径 + 本地仓库路径）管理
- 远程仓库 URL 配置（可选）
- 已安装 Mod 和仓库 Mod 的列表管理与详情查看

**不在范围内：**
- 多游戏管理（当前版本仅支持单一游戏）
- 从远程仓库自动下载 Mod
- Mod 内容的编辑或修改
- 非 zipmod 格式的 Mod 支持（如 BepInEx 插件 `.dll` 文件）
- 卡片内容预览（如角色立绘渲染）
- 从场景卡中提取导出角色卡（规划为 F18，二期实现，见 Q-08）

## 3. 用户分析

### 3.1 目标用户

**典型用户：** Koikatsu 系列游戏玩家，熟悉基本计算机操作，但不具备编程或文件管理专业背景。

| 特征 | 描述 |
|------|------|
| 技术水平 | 普通用户，能够安装软件、浏览文件夹 |
| 使用频率 | 偶尔（下载新 Mod 时、整理 Mod 库时、导入新卡片时）|
| 痛点 | Mod 数量多时容易混乱，拿到卡片不知道缺哪些 Mod，收集的 Mod 散落各处 |
| 核心诉求 | 安装简单、卡片需求一目了然、Mod 按作者归整、不丢失任何收藏 |

### 3.2 用户故事

```
US-01  作为玩家，我希望拖拽 .zipmod 文件来安装 Mod 或添加到仓库，工具自动按作者归类
US-02  作为玩家，我希望安装时能看到 Mod 的名称、作者、版本信息，以便确认是正确的文件
US-03  作为玩家，我希望工具能自动检测重复，阻止重复安装/收藏相同的 Mod
US-04  作为玩家，我希望当存在旧版本时，工具提示我是否升级，而不是静默覆盖
US-05  作为玩家，我希望看到按作者分组的所有 Mod 列表及其当前状态
US-06  作为玩家，我希望能临时禁用某个 Mod 而无需删除它，之后可以重新启用
US-07  作为玩家，我希望卸载一个 Mod 时，相关文件能被干净地清除
US-08  作为玩家，我希望拖入一张角色卡或服装卡，工具告诉我这张卡需要哪些 Mod
US-09  作为玩家，我希望工具告诉我卡片所需的 Mod 中哪些已安装、哪些在仓库中有、哪些缺失
US-10  作为玩家，我希望能配置游戏 Mod 路径和本地仓库路径，分别管理"在用"和"收藏"的 Mod
US-11  作为玩家，我希望拖入一张场景卡，工具告诉我整个场景（含其中所有角色和物品）需要哪些 Mod，以及哪些已安装、哪些在仓库有、哪些缺失
US-12  作为玩家，我希望知道场景中缺失的 Mod 影响的是场景物品还是哪个角色，以便决定是否值得去补齐
```

## 4. 功能需求

> 优先级说明：
> - **P0（必须）**：MVP 阶段必须实现，否则产品不可用
> - **P1（应该）**：v1.0 阶段实现，提升完整性
> - **P2（可以）**：v2.0+ 阶段实现，锦上添花

### 4.1 路径配置（F01）

**优先级：P0**

本工具维护两个核心路径：

| 路径 | 用途 |
|------|------|
| **游戏 Mod 路径** | 游戏 Sideloader 加载 Mod 的目录，放置在此处 = Mod 已安装并在游戏中生效 |
| **本地 Mod 仓库路径** | 用户本地的 Mod 收藏目录，放置在此处 = Mod 已下载但未安装到游戏 |

| 编号 | 需求描述 |
|------|----------|
| F01-1 | 系统应提供游戏 Mod 路径和本地仓库路径两个独立的配置入口 |
| F01-2 | 用户应能通过文件浏览器分别选择两个路径 |
| F01-3 | 两个路径可以为同一目录，也可以是不同目录 |
| F01-4 | 若用户将两个路径设置为同一目录，则"安装"等同于"添加到仓库" |
| F01-5 | 系统应校验所选路径的合法性（路径存在、非空或允许创建） |
| F01-6 | 配置信息应在应用重启后保持不变 |
| F01-7 | 首次启动且未配置路径时，系统应引导用户完成配置 |
| F01-8 | 应能从设置对话框随时修改两个路径 |

---

### 4.2 Mod 元数据解析（F02）

**优先级：P0**

| 编号 | 需求描述 |
|------|----------|
| F02-1 | 系统应能读取 `.zipmod` 文件内的 `manifest.xml` |
| F02-2 | 系统应从 manifest.xml 中提取以下字段：guid、name、version、author、description、website |
| F02-3 | 若 manifest.xml 不存在，系统应提示"此文件不是有效的 zipmod"，并拒绝操作 |
| F02-4 | 若 manifest.xml 格式错误或缺少 guid/name/version 必要字段，系统应提示具体错误 |
| F02-5 | 系统应兼容带 BOM 头的 UTF-8 编码 manifest.xml |
| F02-6 | 解析成功后，在操作确认步骤向用户展示已解析的元数据 |

---

### 4.3 重复安装检测（F03）

**优先级：P0**

重复检测范围：**同时检查游戏 Mod 路径和本地仓库路径**。如果任一位置已存在相同 GUID 的 Mod，即视为重复。

| 编号 | 需求描述 |
|------|----------|
| F03-1 | 系统应在操作前基于 `guid` 字段检测目标路径中是否已有相同 Mod |
| F03-2 | 若检测到 **guid 相同、版本相同**，系统应拒绝操作，提示"已存在相同版本" |
| F03-3 | 若检测到 **guid 相同、新版本更高**，系统应弹出升级确认对话框 |
| F03-4 | 若检测到 **guid 相同、新版本更低**，系统应弹出降级警告对话框 |
| F03-5 | 若未检测到重复，系统应继续操作流程 |
| F03-6 | 升级/降级操作应覆盖旧版本文件 |

---

### 4.4 Mod 安装到游戏（F04）

**优先级：P0**

> **核心逻辑**：安装 = 将 `.zipmod` 文件复制（或移动）到 `{游戏Mod路径}/{作者名}/` 目录下。
> 作者名从 manifest.xml 的 `<author>` 字段提取，**匹配时不区分大小写**。

| 编号 | 需求描述 |
|------|----------|
| F04-1 | 用户应能通过拖放或文件选择对话框选择 `.zipmod` 文件进行安装 |
| F04-2 | 安装前应依次执行：元数据解析 → 重复检测 → 用户确认 → 复制 zipmod 到目标位置 |
| F04-3 | 安装的目标路径为 `{游戏Mod路径}/{分类目录}/{作者名}/{原始文件名}.zipmod`（F19 分类布局；分类开关关闭时回退 `{游戏Mod路径}/{作者名}/...` 旧公式） |
| F04-4 | 若目标作者目录不存在，系统应自动创建 |
| F04-5 | 作者名匹配忽略大小写：例如 `Makise` 和 `makise` 属于同一作者目录 |
| F04-6 | 安装完成后，系统应提示"安装成功"，包含 Mod 名称、版本和安装位置 |
| F04-7 | 安装完成后，游戏 Mod 列表应自动刷新 |
| F04-8 | 安装失败（任意步骤出错）时，系统应回滚已复制的文件并提示错误 |
| F04-9 | 复制操作应在后台线程执行，界面不冻结，应显示进度 |
| F04-10 | 若目标目录下已存在**同名文件**但 manifest.xml 中的版本号不同，系统应自动对新文件进行重命名，规则为：`{原始文件名（不含扩展名）}v{版本号}.zipmod`，例如 `[Makise]GS-Alice.zipmod` → `[Makise]GS-Alicev2.zipmod` |
| F04-11 | 若目标目录下已存在同名文件且版本号也相同，按重复安装检测规则（F03）处理，不执行重命名 |

### 4.5 Mod 添加到仓库（F14）

**优先级：P0**

> **核心逻辑**：添加到仓库 = 将 `.zipmod` 文件复制（或移动）到 `{本地仓库路径}/{作者名}/` 目录下。

| 编号 | 需求描述 |
|------|----------|
| F14-1 | 用户应能将 `.zipmod` 文件添加到本地仓库（与"安装到游戏"为两个独立操作） |
| F14-2 | 添加到仓库时应提供"安装并收藏"快捷操作（相当于先添加到仓库再安装到游戏） |
| F14-3 | 添加的目标路径为 `{本地仓库路径}/{作者名}/{原始文件名}.zipmod` |
| F14-4 | 若目标目录不存在，系统应自动创建 |
| F14-5 | 作者名匹配同样忽略大小写 |
| F14-6 | 若仓库中已存在**同名文件**但版本号不同，同样执行自动重命名：`{文件名（不含扩展名）}v{版本号}.zipmod` |

| 编号 | 需求描述 |

### 4.9 Mod 启用 / 禁用（F08）

**优先级：P1**

> **核心逻辑**：Sideloader 通过检测文件扩展名来判断是否加载 Mod。禁用 = 修改 `.zipmod` 扩展名使其不被加载。

| 编号 | 需求描述 |
|------|----------|
| F08-1 | 用户应能对已安装在游戏中的 Mod 执行禁用操作 |
| F08-2 | 用户应能对已禁用的 Mod 执行启用操作 |
| F08-3 | 禁用操作：将文件扩展名从 `.zipmod` 改为 `.zipmod_disabled`，Sideloader 不再加载 |
| F08-4 | 启用操作：将文件扩展名从 `.zipmod_disabled` 改回 `.zipmod` |
| F08-5 | 仅游戏 Mod 路径下的 Mod 有启用/禁用概念，仓库中的 Mod 无需此功能 |
| F08-6 | 启用/禁用操作完成后，列表中该 Mod 的状态图标应立即更新 |

### 4.10 角色卡 / 服装卡解析（F15）★ 新增核心功能

**优先级：P0**

> **核心逻辑**：用户拖入一张角色卡或服装卡（PNG 格式），工具解析出该卡片所依赖的 Mod GUID 列表，
> 然后依次在"游戏 Mod 路径"和"本地仓库路径"中查找这些 Mod 是否存在，
> 最后生成一份完整的可用性报告。

| 编号 | 需求描述 |
|------|----------|
| F15-1 | 用户应能拖入或选择一张角色卡/服装卡 PNG 文件进行解析 |
| F15-2 | 系统应能从卡片 PNG 文件中提取所依赖的 Mod GUID 列表 |
| F15-3 | 对于每一个依赖 Mod，系统应依次检查： |
|      | ① 该 Mod 是否存在于**游戏 Mod 路径**中（已安装） |
|      | ② 若不在游戏中，该 Mod 是否存在于**本地仓库路径**中（已收藏但未安装） |
|      | ③ 若以上均未找到，标记为**缺失** |
| F15-4 | 解析结果应以列表展示，每个依赖 Mod 标注以下状态： |
|      | **🟢 已安装**：Mod 在游戏 Mod 路径中找到，显示所在作者目录和版本 |
|      | **🟡 仓库有**：Mod 不在游戏中但在仓库中存在，显示可一键安装 |
|      | **🔴 缺失**：Mod 在任何路径中都未找到 |
| F15-5 | 对于状态为"🟡 仓库有"的 Mod，用户应能点击"安装"按钮将其从仓库安装到游戏 |
| F15-6 | 对于状态为"🔴 缺失"的 Mod，系统应汇总缺失列表，方便用户按清单去下载 |
| F15-7 | 解析结果底部应显示统计：总数 / 已安装 / 仓库有 / 缺失 |
| F15-8 | 若卡片解析失败（非有效 PNG 或非卡片文件），系统应给出友好提示 |
| F15-9 | **卡片图片渲染**：解析卡片时，系统应在结果面板顶部渲染并展示该卡片 PNG 的图片内容，供用户直观确认是哪张卡片 |

### 4.15 场景卡解析（F17）★ 新增

**优先级：P0**

> **核心逻辑**：场景卡是 Koikatsu Studio 保存的 PNG 场景数据文件，其 Mod 依赖存在于两处：
> ① **场景级扩展数据块**（文件尾部【KStudio】标识之后的 KKEx 块）中 Sideloader
> UniversalAutoResolver 记录的物品 / 图案 / 地图 / 滤镜 / Ramp / BGM 依赖；
> ② **每个内嵌角色**（场景对象树中的 CHARACTER 对象，各携带一份完整角色卡数据）
> 的 KKEx 依赖列表 —— 与角色卡解析（F15）同源，可直接复用其解析逻辑。
> 两组来源提取后按 GUID 合并去重，再按 BR-C03 顺序做可用性检查。

| 编号 | 需求描述 |
|------|----------|
| F17-1 | 用户拖入或选择任意卡片 PNG 时，系统应自动识别卡片类型：服装卡（KoiKatuClothes 标识）/ 场景卡（【KStudio】标识）/ 角色卡（【KoiKatuChara】标识），并进入对应解析流程；识别入口与 F15 统一 |
| F17-2 | 系统应加载并展示场景摘要信息：场景数据版本、内嵌角色数 / 物品数等对象统计、地图、内嵌角色名单（昵称）、是否为 Timeline 动画场景 |
| F17-3 | 系统应从场景级扩展数据块中提取 Mod 物品与图案依赖（`itemInfo` / `patternInfo` 列表，逐条 msgpack 解码提取 GUID） |
| F17-4 | 系统应提取地图 / 滤镜 / Ramp / BGM 依赖（`mapInfoGUID` / `filterInfoGUID` / `rampInfoGUID` / `bgmInfoGUID` 字符串字段，存在时） |
| F17-5 | 系统应遍历场景内嵌角色，逐个复用角色卡解析逻辑（F15-2）提取 Mod 依赖 |
| F17-6 | 同一 GUID 被多个来源（多个角色 / 场景物品）引用时，应合并为一条依赖记录并保留全部来源（来源类型：场景物品 / 地图等，或"角色：昵称"） |
| F17-7 | 对 🔴 缺失的 Mod，系统应展示其随卡携带的元数据（Author / Name / Website，来自卡内 UAR 数据），复制缺失清单时应包含这些下载线索 |
| F17-8 | 可用性检查、状态标注（🟢/🟡/🔴）、一键安装与全部安装、复制缺失列表等复用 F15-3 ~ F15-7 的既有规则与交互 |
| F17-9 | 解析结果面板复用 7.2 布局：左侧为场景缩略图与摘要信息（含 Timeline 徽章），右侧为按状态分组的依赖列表，每条依赖的来源以标签形式标注在信息列（见 7.4） |
| F17-10 | 单个内嵌角色数据损坏或解析失败时，应跳过该角色并在结果中标注，不影响其余角色与场景物品的解析 |
| F17-11 | 场景解析应在后台线程执行，解析期间 UI 不冻结，并显示进度（如已处理角色数） |
| F17-12 | 场景卡不提供"转为 KK 卡"功能；非场景数据或损坏的场景卡按 NF-R04 给出友好提示 |

### 4.16 游戏 Mod 分类目录安装（F19）★ 新增

**优先级：P0**

> **核心逻辑**：社区主流实践把 Mods 根下的文件按用途分类存放——官方 Sideloader Modpack 本身就拆成「Sideloader Modpack」与「Sideloader Modpack - Studio」两个子目录，BetterRepack / HF Patch 用户的磁盘上普遍存在 `mods/{分类}/...` 布局。Sideloader **递归加载 Mods 根下所有子目录**，游戏侧对目录层级无感，分类纯粹是玩家的磁盘组织方式。本功能让工具适配该布局：安装时按 Mod 内容类型路由到 `{游戏Mod路径}/{分类}/{作者}/` 三段式目录，并在 GAME 端持久化真实相对路径用于定位。
>
> 已实测验证：Mods 根下多级分类子目录中的 zipmod 游戏加载正常（Q-10）。

| 编号 | 需求描述 |
|------|----------|
| F19-1 | 分类目录功能默认开启；安装到游戏的 Mod 落入 `{游戏Mod路径}/{分类目录}/{作者名}/{文件名}` 三段式路径 |
| F19-2 | 系统维护一份分类目录名清单（默认：AdditionalPoses、BasisAndShaders、ForCharactersLoading、ForStudioScenesLoading、KK_-ExclusivesAndUncensors、KK_-ExtraMaps、MyMods），可在设置对话框中增删改；未知顶层目录视为用户手动分类，照常扫描与记录 |
| F19-3 | 安装时应按 zipmod 包内容自动识别 Mod 类型（识别规则见 BR-CAT02）：`chara`（角色服装部件）/ `studio`（工作室物品、地图）/ `both`（两者皆有）/ `other`（其余，如姿势包、材质着色器、解码补丁） |
| F19-4 | 类型到分类目录的默认映射：`chara` → ForCharactersLoading、`studio` → ForStudioScenesLoading、`both` → ForCharactersLoading、`other` → MyMods；映射可在设置中修改 |
| F19-5 | 关闭分类开关时，安装回退到 `{游戏Mod路径}/{作者名}/` 旧公式（完全兼容现状） |
| F19-6 | GAME 端记录应持久化 `game_relative_path`（相对游戏 Mods 根的 POSIX 路径）；卸载/启停/移除定位时优先使用它，为空时回退「分类/作者」推导公式——与 REPO 端 `repo_relative_path` 策略对称 |
| F19-7 | 磁盘同步/重扫的作者推断护栏：已知分类目录名不得被推断为作者名（BR-CAT03） |
| F19-8 | 存量数据库升级时应自动幂等补列（`mod_type`、`game_relative_path` 及历史遗留的 `repo_relative_path`）；存量 GAME 端旧布局文件**不自动搬动**，重新安装后自然归入分类 |
| F19-9 | Mod 详情面板展示内容类型与游戏相对路径；安装确认对话框显示目标分类 |
| F19-10 | 卡片解析（F15/F17）的「安装 / 全部安装」按 Mod 记录的类型自动路由到对应分类目录（主用例：角色卡缺失多为 chara 类，场景卡缺失按 chara/studio 分流到对应分类） |
| F19-11 | 仓库端不应用分类布局，维持 `{仓库路径}/{作者名}/` 现状（决策依据见 Q-10） |

## 5. 业务规则

### 5.1 作者目录命名规则

| 规则编号 | 规则描述 |
|----------|----------|
| BR-A01 | Mod 文件按作者名归类存放到子目录，目录名来源于 manifest.xml 的 `<author>` 字段 |
| BR-A02 | **作者名匹配忽略大小写**。`Makise`、`makise`、`MAKISE` 视为同一作者，归入同一目录 |
| BR-A03 | 若 author 字段为空，归入 `Unknown` 目录 |
| BR-A04 | 作者目录名为规范化后的作者名（首字母大写的原始拼写），而非全小写或全大写 |

### 5.2 重复检测规则

| 规则编号 | 规则描述 |
|----------|----------|
| BR-D01 | **相同 GUID + 相同版本 = 拒绝操作**。系统不允许在目标路径中放置与现有 Mod GUID 和版本完全相同的 Mod |
| BR-D02 | **相同 GUID + 版本不同 = 需用户确认**。系统不允许静默覆盖，必须弹出对话框由用户决定是否升级/降级 |
| BR-D03 | **重复检测范围**：仅检测目标路径（游戏 Mod 路径或仓库路径），两个路径独立管理 |
| BR-D04 | 游戏和仓库中可以同时存在相同 GUID 的 Mod（一个在用，一个收藏），这不属于重复 |
| BR-D05 | **GUID 唯一性**（在单个路径范围内）。数据库中对同一路径下的 GUID 施加唯一约束 |

### 5.3 版本比较规则

| 规则编号 | 规则描述 |
|----------|----------|
| BR-V01 | 系统应优先使用语义化版本规范（如 `1.0.0 > 0.9.0`）进行版本比较 |
| BR-V02 | 若版本号格式不符合语义化规范，系统应尽力解析，并告知用户版本格式不标准 |
| BR-V03 | 版本比较失败时，系统应保守处理（假定为"版本不同，不确定新旧"） |

### 5.4 卡片解析规则

| 规则编号 | 规则描述 |
|----------|----------|
| BR-C01 | 卡片必须是有效的 PNG 格式文件 |
| BR-C02 | 卡片内嵌的 Mod 依赖数据以 GUID 列表形式存在 |
| BR-C03 | 卡片解析结果的可用性判断顺序：先查游戏 Mod 路径，再查本地仓库路径 |
| BR-C04 | 若卡片所需的某一 Mod 在游戏和仓库中均存在但版本不同，以游戏中版本为准标注"已安装" |
| BR-C05 | 卡片类型识别依据（PNG IEND 之后的数据块特征）：服装卡含 `KoiKatuClothes` 标识，场景卡含 `【KStudio】` 标识，角色卡含 `【KoiKatuChara】` 标识 |
| BR-C06 | 场景卡 Mod 依赖取自两处：场景级扩展数据块的 Sideloader UAR 数据（物品 / 图案 / 地图 / 滤镜 / Ramp / BGM）+ 各内嵌角色 KKEx 的 UAR 依赖列表（后者复用角色卡解析规则 BR-C02） |
| BR-C07 | 依赖合并规则：同一 GUID 被多个来源引用时合并为一条记录，来源以列表保留；可用性状态以 GUID 为准判定，与来源无关 |
| BR-C08 | 内嵌角色容错规则：单个角色解析失败时跳过并在结果中标注，不影响其他角色与场景物品的解析结果 |

### 5.5 文件操作规则

| 规则编号 | 规则描述 |
|----------|----------|
| BR-F01 | `.zipmod` 文件就是 Mod 本身，安装 = 复制 zipmod 到目标目录，不涉及解压 |
| BR-F02 | 卸载/移除 = 删除对应的 `.zipmod`（或 `.zipmod_disabled`）文件 |
| BR-F03 | 禁用 = 修改文件扩展名，不移动文件位置 |
| BR-F04 | 操作前应确认目标路径有写入权限 |
| BR-F05 | **同名文件重命名规则**：目标目录下已存在同名 zipmod 但版本不同时，新文件重命名为 `{原文件名（不含扩展名）}v{版本号}.zipmod`。例如：原名 `[Makise]GS-Alice.zipmod`，新版本号为 `2`，则重命名为 `[Makise]GS-Alicev2.zipmod` |
| BR-F06 | 重命名后的文件名若仍与目标目录内已有文件冲突（概率极低），在版本号后追加 `_{序号}` 以保证唯一性，例如 `[Makise]GS-Alicev2_1.zipmod` |

### 5.6 GUID 说明

| 规则编号 | 规则描述 |
|----------|----------|
| BR-G01 | GUID 由 Mod 作者在 manifest.xml 中定义，可包含特殊字符（如方括号、空格） |
| BR-G02 | 若不同 Mod 的 GUID 相同（属社区上游问题），工具应阻止第二个 Mod 的安装，并提示用户手动处理 |

### 5.7 分类目录规则（F19）

| 规则编号 | 规则描述 |
|----------|----------|
| BR-CAT01 | 分类目录与作者目录使用同一套目录匹配机制（忽略大小写复用磁盘上已存在的目录）；分类开关关闭时安装回退 `{游戏Mod路径}/{作者名}/` 旧公式 |
| BR-CAT02 | 类型识别规则：zip 内条目路径（统一小写、反斜杠归一为正斜杠后）以 `list/characustom/` 开头 → chara；以 `abdata/studio/` 或 `abdata/map/` 开头 → studio；两者皆有 → both；否则 → other。仅含 manifest.xml 的最小包判为 other |
| BR-CAT03 | 作者推断护栏：对 manifest 无作者的 Mod，取文件相对 Mods 根的目录段**自底向上找第一个不属于分类清单的段**作为作者名；全为分类段或文件直躺在 Mods 根下 → 归入 Unknown。**护栏不受分类开关控制**（关闭开关后磁盘上的分类布局仍需正确扫描） |
| BR-CAT04 | 仓库端不应用分类布局：REPO 记录的目录组织与定位公式（`repo_relative_path` 优先）保持不变 |
| BR-CAT05 | 分类目录名为保留名：与作者名撞名时（如作者恰好叫 MyMods），无 manifest 作者的记录不以目录名推断作者；有 manifest 作者的记录以 manifest 为准（元数据优先）。用户可通过修改分类清单释放名称 |
| BR-CAT06 | 卸载后清理空目录时排除分类目录（分类目录即使被清空也不删除） |

## 8. 数据需求

### 8.1 持久化数据

本工具需持久化以下类型数据：

**Mod 记录**（每个 Mod 的每个位置一条记录）：

| 字段 | 类型 | 说明 |
|------|------|------|
| guid | 字符串 | 来自 manifest.xml，重复检测依据 |
| name | 字符串 | Mod 显示名称 |
| version | 字符串 | 版本号 |
| author | 字符串 | 作者名（作为目录分类依据） |
| author_normalized | 字符串 | 规范化后的作者名（用于目录创建和匹配） |
| description | 字符串 | 描述，可为空 |
| website | 字符串 | 作者网站，可为空 |
| file_name | 字符串 | zipmod 文件名，如 `[Makise]GS-Alice.zipmod` |
| location | 枚举 | 位置：`GAME`（游戏已装）或 `REPO`（仓库） |
| status | 枚举 | 状态：`ENABLED`（启用）、`DISABLED`（禁用），仅 GAME 位置的有效 |
| installed_at | 时间戳 | 安装或添加时间 |
| notes | 字符串 | 用户自定义备注 |
| repo_relative_path | VARCHAR(1000) | 仓库 Mod 相对路径（仅 REPO 端使用，GAME 端为空）；格式如 `Makise/[Makise]GS-Alice.zipmod`，为空时按 `作者目录/文件名` 回退定位 |
| mod_type | VARCHAR(20) | Mod 内容类型：`chara` / `studio` / `both` / `other`（识别规则见 BR-CAT02）；空 = 老数据未识别，路由时按 `other` 处理并在下次安装/同步时回填 |
| game_relative_path | VARCHAR(1000) | 游戏 Mod 相对路径（仅 GAME 端使用，REPO 端为空）；格式如 `ForStudioScenesLoading/Zelwent/Zelwent.FairyWings.zipmod`，为空时按「分类目录/作者名/文件名」回退定位 |

> 注意：同一个 Mod（相同 GUID）可以同时存在于 GAME 和 REPO 两条记录中，
> 此时 GAME 记录表示"已安装到游戏"，REPO 记录表示"仓库中有收藏"。

**路径约定**：
- **GAME 端**：优先用 `game_relative_path` 定位文件（文件名部分按当前启停状态替换，兼容 `.zipmod` ↔ `.zipmod_disabled` 改名）；为空时回退到 `game_mod_path / 分类目录 / 作者名 / 文件名`（分类开关关闭或老数据时为 `game_mod_path / 作者名 / 文件名`）。
- **REPO 端**：优先用 `repo_relative_path` 定位文件；`repo_relative_path` 为空时回退到 `repo_path / 作者名 / 文件名`。
- 相对路径字段统一使用 POSIX 风格（正斜杠 `/`），如 `ForCharactersLoading/Makise/[Makise]GS-Alice.zipmod`。

**应用配置**（JSON 文件）：

| 配置项 | 说明 |
|--------|------|
| game_mod_path | 游戏 Mod 路径（Sideloader Mods 目录） |
| repo_path | 本地 Mod 仓库路径 |
| remote_repo_url | 远程仓库 URL（可选，可为空） |
| 界面主题 | 暗色 / 亮色 |
| 行为配置 | 卸载前确认、卸载后清理空目录等 |
| 分类目录配置 | 游戏分类目录安装开关、分类目录清单、类型默认分类映射（F19） |

### 8.2 目录结构示例

```
{游戏Mod路径}/ （F19 分类布局，默认开启）
├── AdditionalPoses/               # 额外姿势
│   └── {作者名}/姿势包.zipmod
├── BasisAndShaders/               # 基础材质与着色器（很多 Mod 的前置）
│   └── {作者名}/...
├── ForCharactersLoading/          # 角色卡加载所需（服装/发型/饰品）
│   ├── Makise/[Makise]GS-Alice.zipmod
│   └── moderchan/moderchan.CharamakerSupportMOD.zipmod
├── ForStudioScenesLoading/        # 工作室场景所需（地图/道具/特效）
│   └── Zelwent/Zelwent.FairyWings.zipmod
├── KK_-ExclusivesAndUncensors/    # 恋活专属内容与解码补丁
│   └── {作者名}/...
├── KK_-ExtraMaps/                 # 额外地图
│   └── {作者名}/...
├── MyMods/                        # 手动兜底分类（other 类默认落点）
│   └── {作者名}/...
└── Unknown/                       # 无作者 Mod 兜底（位于分类之下或旧布局根下）

{本地仓库路径}/ （不分类，维持作者目录）
├── Makise/
│   ├── [Makise]GS-Alice.zipmod
│   └── [Makise]OldMod.zipmod
├── SomeAuthor/
│   └── HairPack_v1.zipmod
└── Unknown/
    └── ...
```

> 备注：分类开关关闭时，GAME 端退回单层 `{作者名}/` 布局（即 v1.4 及之前的示例）；无作者 Mod 归入所在层级的 `Unknown/` 目录。

### 8.3 数据存储位置

所有数据文件均存储在 **exe 程序所在目录**下，不写入用户目录或注册表，方便整体打包迁移。

| 数据类型 | 存储位置 |
|----------|----------|
| Mod 数据库 | `{exe所在目录}/data/mods.db`（SQLite） |
| 应用配置 | `{exe所在目录}/data/config.json` |
| 运行日志 | `{exe所在目录}/logs/`（按日期滚动） |

> 注：`{exe所在目录}` 指 `.exe` 可执行文件所在的文件夹，即 `sys.executable` 或 `__file__` 的父目录。程序运行时若 `data/` 和 `logs/` 目录不存在应自动创建。

## 9. 约束与假设

### 9.1 技术约束

| 约束 | 说明 |
|------|------|
| 目标平台 | Windows 10/11，64 位 |
| 运行方式 | 本地桌面应用，不依赖网络（远程仓库为可选配置） |
| 文件格式 | 仅支持 `.zipmod` 格式 |

### 9.2 设计假设

| 编号 | 假设内容 |
|------|----------|
| A-01 | `.zipmod` 文件本身即 Mod，Sideloader 可直接读取，无需解压安装 |
| A-02 | 同一 Mod 的所有版本共享相同的 GUID（Mod 社区约定） |
| A-03 | 作者名来自 manifest.xml 的 `<author>` 字段，忽略大小写进行匹配和归类 |
| A-04 | 角色卡、服装卡和场景卡为 PNG 格式，内嵌 Mod 依赖数据 |
| A-05 | 用户对配置的路径拥有读写权限 |
| A-06 | 游戏 Mod 路径默认指向 Sideloader 的 Mods 目录（如 `BepInEx/plugins/` 或自定义路径） |

### 9.3 已知风险

| 风险 | 说明 | 应对策略 |
|------|------|----------|
| 同 GUID 不同内容的 Mod | 少数非官方重打包 Mod 可能 GUID 冲突 | 阻止安装，提示用户手动处理 |
| 版本号格式不规范 | 部分 Mod 版本号无法被语义化解析 | 回退为字符串比较 |
| 作者名为空 | 部分 Mod 的 author 字段为空 | 归入 `Unknown` 目录 |
| 作者名差异（同人不同名） | 同一作者可能使用不同 author 名（如 `makise` vs `Makise` vs `Makise.`） | 忽略大小写可处理大部分情况，精确匹配需用户手动整理 |
| 卡片格式兼容性 | 不同版本游戏的卡片内嵌格式可能不同 | 对无法解析的卡片给出明确提示 |
| 场景卡体积较大 | 场景内嵌多个完整角色数据，文件可达数十 MB，同步解析可能造成界面卡顿 | 后台线程解析并显示进度（F17-11 / NF-P05） |
| 场景物品依赖记录缺失 | 旧版 Studio 或特殊来源的场景可能缺少场景级 UAR 数据，物品依赖无法提取 | 依赖列表以实际解析到的数据为准；无物品依赖时正常展示角色依赖与摘要信息 |

## 10. 待确认问题

| 编号 | 问题 | 影响范围 | 结论 |
|------|------|----------|------|
| Q-01 | 是否需要支持批量安装（选择一个文件夹，扫描其中所有 `.zipmod` 一次性安装/添加到仓库）？ | F04 / F14 | **第一版暂不实现**，后期版本保留此功能入口 |
| Q-02 | "安装并收藏"操作中，Mod 是先复制到仓库再从仓库安装到游戏，还是分别从源文件复制两份？ | F14 / F04 | **先复制到仓库，再从仓库安装到游戏**（仓库是唯一来源） |
| Q-03 | 远程仓库需要在哪个版本中实现实际查询功能？ | F16 | **第一版仅作 URL 配置预留，不实现远程查询逻辑** |
| Q-04 | 卡片解析中，若游戏和仓库中相同 GUID 的 Mod 版本不同（如游戏 v1、仓库 v2），如何处理？ | F15 / BR-C04 | **提示用户版本存在差异**，显示两个位置的版本号，由用户决定是否升级 |
| Q-05 | 是否需要在卡片解析结果中提供一键安装"仓库有"的全部 Mod 功能？ | F15 | **需要**，在解析结果面板中提供"全部安装"按钮 |
| Q-06 | 场景解析结果的分组方式：按状态分组（现有 F15 布局）还是按来源（角色 / 场景物品）分组？ | F17 / 7.4 | **按状态分组，来源以标签标注在信息列**——与现有面板一致、改动最小，来源信息完整保留（US-12 的诉求通过来源标注满足） |
| Q-07 | 场景解析是否需要后台线程？ | F17 / NF-P05 | **需要**。大型场景内嵌角色多、解析耗时可能超过 NF-P03 的同步阈值，参照 NF-P04 在后台线程执行并显示进度 |
| Q-08 | 是否支持从场景卡提取内嵌角色另存为角色卡？ | F17 范围 | **二期实现（F18，P2）**。技术可行（内嵌角色为完整角色卡数据），但场景内嵌角色不含卡面立绘 PNG，需设计占位图 / 自定义卡面方案（参考同类工具 IllusionStudioGet 的做法） |
| Q-09 | 是否支持一次拖入多张场景卡批量检查并汇总缺失清单？ | F17 范围 | **二期考虑**，当前版本聚焦单张场景卡的完整解析闭环 |
| Q-10 | 玩家把人物 Mod 与工作室 Mod 分类存放于 Mods 根的子目录（社区主流布局），工具如何适配？ | F04 / F19 / BR-CAT | **游戏端采用三段式安装路径 `{Mods根}/{分类}/{作者}/` + mod_type 自动识别路由 + game_relative_path 持久化定位**（已实测 Mods 根子目录递归加载正常）；分类功能默认开启、清单与映射可配置；**仓库端不加分类**（维持 `{仓库}/{作者}/`，不同用户仓库组织各异且无加载器约束）；存量旧布局文件不自动搬动，重新安装后自然归位 |
